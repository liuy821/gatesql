# 技术决策记录（ADR）

> **这份文档的价值在于让面试官看到：技术栈不是随便选的，每个选择背后都有权衡，而且你知道自己付出了什么代价。**
>
> 写不出「代价」一节的决策，说明没想清楚 —— 退回去重想。

格式：背景 → 决策 → 理由 → 被否决的备选 → 代价。

## ADR-001 · 用 Next.js 全栈单体，不拆前后端

**背景**：原计划是 Next.js 前端 + FastAPI 后端。

**决策**：单一 Next.js 16 应用（App Router），前后端同仓同进程。

**理由**：单人全栈项目，两个语言栈会让部署、类型同步、本地开发都变复杂；SSE 事件协议在同一个 TypeScript 仓库里能做到编译期契约检查，跨语言就只能靠文档。

**否决的备选**：FastAPI + Next.js 分离（要维护两套依赖、两个容器、手工同步类型）；独立常驻 Node worker 进程（实质违背「Next.js 全栈」，「同一个仓库、换个进程入口」是辩解不是符合）。

**代价**：放弃 Python 的数据生态（pandas 等）；`node:sqlite` 相对 Python 的 sqlite3 生态更新、资料更少；长流式请求与 serverless 部署天然冲突（因此 ADR-010 选了自托管容器）。

## ADR-002 · 用 `node:sqlite`，不用 `better-sqlite3`

**背景**：需要一个能在 Node 里跑 SQLite、且能做安全管控的驱动。

**决策**：Node 24 内置的 `node:sqlite`（`DatabaseSync`）。

**理由**：两条，都是实测出来的 ——

1. **它有 `setAuthorizer`**，这是整个安全叙事的核心（见 [安全设计](07-security.md#第-2-层--引擎级授权回调安全叙事的核心)）。`better-sqlite3` 完全没有授权回调能力。
2. **零原生编译**。`better-sqlite3` 需要 node-gyp，Windows 上要 VS Build Tools、Docker 里要处理 musl 编译，是双重雷区。

**否决的备选**：`better-sqlite3`（选它的唯一理由是想要 `db.interrupt()` 做硬超时，但实测 **13.0.3 根本没有 `interrupt` 方法**；而且即使有也不成立 —— db 句柄归 worker 所有，主线程无法调它的方法，postMessage 进去也没用，因为 worker 的事件循环正被同步原生调用堵死）。

**代价**：`node:sqlite` 是同步 API，一条慢查询会冻住整个事件循环，必须靠 worker 隔离（ADR-003）；API 较新，社区资料少。

## ADR-003 · 查询超时靠「预防 + 放弃等待」，不靠 `terminate()`

**背景**：同步驱动 + 慢查询 = 服务假死。需要超时机制。

**决策**：三件事的组合 ——
1. EQP 代价预检做**预防**（1ms，在执行前拦住笛卡尔积）
2. 超时后主线程**放弃等待**，把该 worker 标记污染移出池，补建新 worker
3. 容器层 SIGTERM → SIGKILL 兜底

**理由**：实测 `worker.terminate()` 对卡在同步原生调用里的 worker **永远不 resolve**（15 秒无反应，连 `process.exit(0)` 都无法让进程退出）。但主线程全程健康 —— 所以 worker 隔离保的只是服务可用性，不是超时本身。

**否决的备选**：依赖 `worker.terminate()`（被实测证伪）；`child_process` 级隔离（SIGKILL 确实能真正回收，但在预防已足够可靠时不值得，且 GBK 环境下 stdio 编码是额外雷区）。

**代价**：卡死的 worker 会占着内存直到进程退出；优雅关闭失效，容器必须配 SIGKILL 超时。

## ADR-004 · 不迁移到 PostgreSQL

**背景**：多份方案都主张迁 PG，理由是「独立只读角色 + `SET TRANSACTION READ ONLY` + `statement_timeout` + `pg_cancel_backend`」的安全叙事更硬。

**决策**：继续用 SQLite。

**理由**：`setAuthorizer` 拿到的是 SQLite 解析后的 `(action, 表, 列)` 三元组，**比只读角色更细粒度**，而且能挡住 CTE 里藏的写操作。PG 方案是为一个已经有更好答案的问题付账。

**否决的备选**：PostgreSQL（代价是多一个容器、双连接池双凭据、种子脚本改写并保证两引擎评测答案一致、SQL 方言适配层）。

**代价**：失去服务端异步取消（`pg_cancel_backend` 确实比「放弃等待」更彻底）；失去真实企业数据库的简历观感。对冲：在 backlog 里写清「如果要上 Postgres 会怎么做」，面试时讲出来 —— **讲得清楚和做出来在面试里价值接近，成本差二十倍**。

## ADR-005 · 不引入 ORM

**背景**：Next.js 项目通常配 Prisma 或 Drizzle。

**决策**：不用 ORM，`node:sqlite` 的 `prepare` + 手写 SQL。

**理由**：`shop.db` 是运行时才知道结构的**被分析库**，ORM 的编译期类型在这里没有意义，而且 agent 必须走原始 SQL 字符串；`app.db` 只有 6 张表、访问模式固定，加一层 ORM 是纯负担（还会增加 Docker 体积和迁移工具依赖）。

**否决的备选**：Drizzle（更轻，但仍解决不了「被分析库结构运行时才知道」这个根本问题）；Prisma（引擎二进制体积大，与单容器目标冲突）。

**代价**：失去类型安全的查询构造器。对冲：`app.db` 每张表在 `src/types/db.ts` 有对应 TS 类型，所有查询收敛到 `src/lib/db/app.ts` 一个文件，其他地方不允许直接写 SQL。

## ADR-006 · 流式用 Route Handler + ReadableStream，CRUD 用 Server Actions

**背景**：App Router 提供了两种服务端能力，需要明确边界。

**决策**：长时流式问答走 Route Handler 返回 `ReadableStream`（手写 SSE）；报表与纠正样本的增删改走 Server Actions。

**理由**：Server Actions 不支持流式增量返回，而 agent 的多步过程必须实时推给用户；反过来，短事务 CRUD 用 Server Actions 能天然拿到 CSRF 防护和 `revalidatePath`，写 REST 接口是多余的。

**否决的备选**：全部走 Route Handler（CRUD 要手写一堆样板）；用 `EventSource` 消费（它只能 GET 且不能带自定义头）；WebSocket（双向能力用不上，还多一层连接管理）。

**代价**：项目里存在两种服务端调用范式，新人需要理解边界 —— 但这条边界判断本身就是面试可讲的内容。

## ADR-007 · SSE 事件协议用 Zod discriminated union 作为唯一契约

**背景**：前端、Route Handler、评测脚本三方都要消费事件。

**决策**：事件类型定义在 `src/lib/events.ts`，三方 import 同一份；前端 switch 加 `satisfies never` 穷尽检查；接口文档由类型生成。

**理由**：**把协议漂移从「靠 code review 发现」升级为「编译失败」。**

**否决的备选**：手写 TypeScript interface（没有运行时校验）；OpenAPI + 代码生成（重，且 SSE 的事件流描述能力弱）。

**代价**：Zod 的运行时校验有轻微性能开销；事件类型增多时 union 会变长。

## ADR-008 · 安全 fail-closed，口径 lint fail-open

**背景**：guard 和 lint 都用 `node-sql-parser`，都会遇到解析失败。

**决策**：**同一个解析器，两条相反的失败策略。** guard 解析失败即拒绝；lint 解析失败放过并记 warn。

**理由**：安全上「拒绝」是安全侧 —— 解析不了的 SQL 宁可不执行；可用性上「放过」是安全侧 —— 口径检查失败不该阻断一个可能完全正确的查询。

**否决的备选**：两边都 fail-closed（解析器不支持的合法 SQL 会被误杀，拉低准确率）；两边都 fail-open（安全防线形同虚设）。

**代价**：这个不对称需要在代码里写清楚注释，否则后来者会以为是 bug。

## ADR-009 · 不用向量检索

**背景**：few-shot 召回和 schema 检索的常规做法是向量相似度。

**决策**：确定性的关键词 + 表名重叠打分。

**理由**：**不是「4 张表用不上检索」这个层次的理由。真实理由是：向量召回引入不确定性，同一道评测题两次跑出不同上下文，准确率变化再也无法归因 —— 它会摧毁花两周建起来的评测体系。**

**否决的备选**：pgvector、内存向量库、embedding + 余弦相似度。

**代价**：召回质量弱于语义检索；表数量大幅增长后需要换方案。对冲：裁剪函数从第一天就存在且可关闭，面试时能回答「表涨到 300 张怎么办」。

> 这条是「为了可评测性主动放弃更花哨的技术」，**这个取舍本身比技术选择更能体现工程成熟度**。

## ADR-010 · 部署用 Docker 单容器，不用 Vercel

**背景**：Next.js 的默认部署目标是 Vercel。

**决策**：`output: 'standalone'` + 多阶段 Dockerfile，单容器自托管。

**理由**：serverless 文件系统只读且实例间不共享，`app.db` 的 trace 和报表写不进去；函数执行时长上限与长流式 run 冲突。

**否决的备选**：Vercel（上述两个硬冲突）；Kubernetes / Helm（单人项目引入这些是自证不懂取舍）。

**代价**：需要自己管服务器和 HTTPS；冷启动和扩容都得手动。

## ADR-011 · 鉴权只做单口令 JWT

**背景**：公网部署需要防止 API key 被刷爆。

**决策**：单一共享口令 + `jose` 签 httpOnly cookie + middleware 拦截 + IP 限流 + 日 token 预算（超限降级 replay）。

**理由**：真实目标只有一个 —— 别让 key 被刷穿。这十几行代码完全达成目标。

**否决的备选**：Auth.js / NextAuth + OAuth（应用注册、回调地址、数据库 adapter、session 策略是几天样板配置，换来**零简历价值** —— 没有面试官会因为你会配 NextAuth 而加分）。

**代价**：没有多用户和权限体系。但这与「不接用户自己的数据库」的定位一致，不是缺陷。

> 「超预算降级到 replay 而不是报 500」这个设计本身是加分点 —— 它保证面试官任何时候打开链接都能看到东西。

## ADR-012 · 不用任何 agent 框架

**背景**：LangChain / LangGraph / LlamaIndex 能显著减少代码量。

**决策**：手写主循环，不引入框架。

**理由**：项目的核心价值就是「我设计了这个循环并能讲透它」。一行 `import` 换掉整个项目的价值。

**否决的备选**：LangGraph（状态机抽象确实合适，但它会让「重试怎么防死循环」变成「框架帮我处理的」）。

**代价**：多写约 250 行代码；要自己处理结构化输出容错、重试分流、预算管理。**这些恰恰是面试要问的部分，所以代价即收益。**

## ADR-013 · 30 题评测集，不是 120 题

**背景**：更大的评测集统计上更可靠。

**决策**：30 题，六层各 5 题。

**理由**：手写 gold SQL 是全部计划中**被最严重低估的工时** —— 30 题就是 2-3 天纯枯燥劳动，且是最可能让人中途崩掉的任务。六层各 5 题足够支撑分层准确率、逐轮优化、由对转错清单的全部叙事。**省下的 3-4 天投给优化轮次 —— 简历上那句带数字的话来自优化轮次，不来自题目数量。**

**否决的备选**：120 题（60 dev + 60 test）。

**代价**：单题权重 3.3%，小样本波动明显。对冲：`temperature=0` + cassette 回放消除模型侧随机性；报分层数字而非只报总分。

## ADR-014 · 不做完整语义层

**背景**：「口径由代码保证」的终极形态是 QueryPlan IR + 确定性 SQL 编译器 + join 路径求解器。

**决策**：只做 8 条口径规则 + AST 谓词到达性检查。

**理由**：完整语义层通往 Cube.js 克隆。4 张表的 join 路径写死是十几行代码，通用求解器是几周且面试零加分 —— 面试官想听的是「哪些约束该由代码保证、哪些交给模型」，不是「我实现了路径求解」。8 条规则拿走它约 **80% 的叙事**，成本 3-4 天而不是 3 周。

**否决的备选**：完整 IR + 编译器 + 粒度冲突检测 + 方言编译层。

**代价**：规则是枚举的，覆盖不到的口径形态只能落「未核验」。**这个代价是可接受的 —— 三态输出本来就承认「有些答案我不敢打包票」。** 剩下 20% 写进 backlog 说「如果要做会怎么做」。

> 这条决策的失败模式是隐蔽的：语义层滑坡两周，第 6 周拿不到准确率上升曲线，而那条曲线是整个项目的**全部**简历价值。

## ADR-015 · 不做自由多轮追问（会话化押后）

**背景**：取数产品的自然终局是「那上个月呢？」这种指代追问。

**决策**：只做一键澄清（歧义拒答 → 点选项 → 原问题 + 口径话术自动重问）；自由多轮会话押后。

**关键问题**：多轮 = 有状态 = 同一题两次跑出不同结果，摧毁评测可复现性——与向量检索同级别风险。且 `/api/chat` 契约第一天就预留了 `conversationId`（恒传 null），真做是填坑不是改契约。

**如果做**：conversations 表 + runs 外键 → loop 注入会话上下文 → 前端聊天线程 → 另起多轮题集。

**触发条件**：出现真实追问需求，或作品集要展示会话化能力——但必须连评测扩展一起做。

## ADR-016 · 环路检测指纹：语义归一边界

**背景**：防模型震荡需要给每条 SQL 算指纹；「语义等价」的水深不见底。

**决策**：只认两条**可证明安全**的等价——①AND/OR 操作数排序（交换律）；②列引用别名归约为真实表名。明确不碰：JOIN 顺序、`x<=5` vs `x<6`、子查询↔JOIN 改写。

**关键问题**：**误杀比漏抓代价大**——漏抓只是多烧预算（文本指纹和计数器兜底）；误杀会把模型真实的改动当震荡掐死。

**护栏**：AND 叶子按整条序列化排序，操作数集合不同（哪怕只换值）就是不同指纹。

**代价**：`x<=5`↔`x<6`、子查询改写类震荡仍抓不到——有 execRetries 兜底，可接受。7 单测锁死边界。

## ADR-017 · 口径回执只翻译规则表枚举到的谓词形态

**背景**：回执卡是「数字凭什么可信」的证据，自然想翻译得越多越好。

**决策**：只翻译枚举形态（R1 + 时间范围）；lint 认不出的等价写法宁可整行不出现，绝不硬编。

**关键问题**：回执的价值在「模型不可见、代码机械生成」——一旦让模型参与翻译或硬编模糊措辞，卡片就结构性可能撒谎，「已核验」可信度崩。（语义修正实录：纯计数查询无口径声明义务，不算翻译不全——曾误降级，已修。）

**代价**：部分合法写法拿不到完整回执。对冲：如实落「未核验」+ 说明，宁降级不撒谎。

## ADR-018 · trace 表结构第 2 周一次定死

**背景**：trace 是错题归因、回放面板、CI 基线的共同地基，加字段很容易。

**决策**：表结构第 2 周定死；新维度只加在 JSON attributes 列里，不动表结构。

**关键问题**：**每加一个字段都要重跑整套评测才有可比数字**——「本周 vs 上周」的对比全建立在表结构未变的前提上。

**代价**：早期没想到的维度（column_check）只能塞 attributes JSON，查询便利性打折。

## ADR-019 · CI 门禁用 replay，不用 live

**背景**：CI 跑评测可以真调模型（live）也可以 cassette 回放（replay）。

**决策**：门禁强制 replay（--ci 内置），零密钥零花费。

**关键问题**：门禁的全部价值建立在等式「**红灯 = 你的改动坏了**」上。live 的模型是非确定的——红灯可能是模型抽风（假警报），绿灯可能掩盖真回归（漏检）——门禁两个方向同时失效。replay 把模型冻成常量，唯一变量就是代码改动。

**前提**：6C 对齐抽查 10/10 证明 replay ≈ live，确定性替身是忠实的。

**代价**：提示词/模型改动要手工 record 重录才能进基线——刻意为之：改基线必须是显式提交。

## ADR-020 · 口径歧义澄清用确定性词典，不用模型判断

**背景**：「利润率」「复购率」等词有多种合理口径，模型自己不会主动澄清（4 轮实验证明）。

**决策**：确定性词典（keywords 命中 + disambiguators 未点明 → 拒答 + 固定选项）；多轮澄清 = 选项话术（必含 disambiguator）拼回问题自动重问。

**关键问题**：**模型判断「该不该澄清」本身不确定**——可能这次澄清下次瞎算。词典让「该澄清」成为确定性判决，选项人工审定（净利那条甚至写明「选了也算不出」）。

**代价**：词条覆盖有限、有维护成本。**教训实录**：新词条曾误伤评测题 C3/D5——disambiguators 必须对评测题面实测，词条变更必须跑全量 replay（事故催生了 CI 门禁前置自查）。

## ADR-021 · 时间窗口整体越过数据水位 → 提前拒答

**背景**：问「2027 年 1 月的销售额」，旧路径要 1 次 LLM + 执行 + 空集归因，最后才说「范围内没数据」。

**决策**：步骤 1 后若 `resolution.from > asOf`（窗口整体在水位后）→ A4 第二道子检查直接拒答，0 次模型调用（旧编号「步骤 2.6」）。

**关键问题**：**步骤 1 结束时答案就已经可知**——窗口与水位不相交是纯代码可判定，跑 LLM 只是绕路，且拒答理由更精确。

**边界（刻意只做一半）**：只拦「整体在后」。部分重叠（近 30 天跨水位线）照常执行，由步骤 8 出「末端不完整」标记——部分重叠的数据仍有价值；「窗口早于数据起点」需另查 MIN(created_at)，留作后续。

**实测**：2027/E5 均 llmCalls=0、理由精确；B4 部分重叠不受影响。评测无回归。

## ADR-022 · 列名静态核对：零误报纪律

**背景**：模型偶尔幻觉列名，以前靠执行时数据库报错 + 回炉，反馈冷冰冰。

**决策**：lint 后、EQP 前插入 B4（旧编号「步骤 5.5」）——AST 里**带真实表前缀**的列引用对照 PRAGMA 实际列清单；错列执行前拦下，诊断精确到「该表可用列清单」。

**关键问题**：新增检查层最大风险不是漏，是**误杀**——白烧预算 + 冤枉好 SQL。零误报纪律：只核对带前缀且前缀能解析到真实表的引用；无前缀列、CTE 别名、表达式结果一律跳过；解析失败 fail-open；schema 读不到整层静默。

**代价**：CTE 产出列、无前缀歧义列核对不到（漏了有执行层兜底）。

**教训**：这层的误报率与规则误报率同级重要——评测 30 题 cassette 全过零误伤后才敢挂载。

## ADR-023 · 预算耗尽降级 replay，而不是报 500

**背景**：live 模式花真钱，日预算超了怎么办。

**决策**：`applyBudget`——预算 ≥0 且今日已花 ≥ 预算 → live/record **强制降级 replay**，哪怕显式设了 LLM_MODE=live（降级强于显式模式，否则「调 0 再提问」失去意义）；-1 为不限。

**关键问题**：**「预算耗尽报 500」等于把内部账本问题转嫁给用户**——replay 能让面试官任何时候打开链接都有东西看。降级是「有损但可用」，500 是「无损但不可用」——取数产品选前者。

**现状注记**：今日花费恒 0（计价 P2），budget=0 是唯一触发路径；计价落地后同函数自动覆盖部分超支。
