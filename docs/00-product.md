# GateSQL 产品文档

> 一个会对错口径说「不」的中文取数 agent。

## 一、要解决的真问题

不会写 SQL 不是真问题 —— 那件事 ChatGPT 就能做。

Text-to-SQL 在真实业务里唯一的硬障碍是：**它错得很安静**。SQL 语法完全正确、查询成功返回、图也画出来了、模型的文字结论还很自信，但数字是错的，而且没有人能发现。

这不是抽象担忧。在本项目自带的示例库 `data/shop.db` 上，三个陷阱都是现成的：

| 问题 | 错误写法得到 | 正确答案 | 偏差 | 能被发现吗 |
|---|---|---|---|---|
| 总销售额 | 60,765,700.25（漏了 `orders.status='已完成'`） | 41,015,358.75 | 高估 48% | 业务人员会察觉「比我知道的高太多」 |
| 客单价 | 2698.56（`orders→order_items` 的 JOIN 扇出） | 5057.38 | 低估 47% | 勉强能察觉 |
| 销售额 | 43,560,642.14（用 `products.price` 而非成交价 `order_items.unit_price`） | 41,015,358.75 | **仅高 6.2%** | **没有任何人能发现** |

第三行才是这个产品存在的理由。一个只偏 6.2% 的数字会被当成真的，然后进入周报、进入决策。这就是企业不敢把 Text-to-SQL 真正上线的原因。

**GateSQL 把全部工程量押在一件事上：一个看起来对的数字，凭什么被相信。**

## 二、产品定位

GateSQL 服务一个明确的纵向场景：一个已知的、有脏数据和业务陷阱的电商库（`customers` / `products` / `orders` / `order_items`），让不会写 SQL 的运营和业务人员用中文问数。

它**不做**通用 BI，**不做**聊天机器人，**不接**用户自己的数据库。用这些范围上的放弃，换三件 demo 做不到的事：

1. **口径由代码强制，而不是靠提示词祈祷** —— 8 条业务口径规则以 SQL AST 谓词到达性检查的形式在执行前生效，违规不是挂个黄色警告，而是带着「缺失的具体谓词」回喂模型重新生成
2. **答案带三态可信度标注** —— 已核验 / 未核验（写明具体原因）/ 拒答（给澄清选项），拒答是系统基于确定性信号做出的判断，与「模型说不知道」是两回事
3. **准确率可被一条命令复现和回归** —— 30 题冻结评测集 + LLM 请求录制回放，CI 里掉点直接让 PR 变红

判断标准很简单：**demo 的验收标准是「跑通了」，GateSQL 的验收标准是「错答会被它自己拦下，而且这件事有数字、能复现、PR 里会变红」。**

## 三、目标用户

| 用户 | 他们的处境 | GateSQL 给他们什么 |
|---|---|---|
| 电商运营 / 商品负责人 | 每天要看销售额、渠道占比、分类毛利，会用 Excel 但不会写 JOIN，只能把需求提给分析师排队 | 中文问数 + 看得懂的口径回执（他们读不了 SQL，但读得懂「已排除已取消 1873 单」） |
| 中小团队里唯一的分析师 | 60% 时间被重复的临时取数打断 | 把常规问题挡在自己前面，生成的 SQL 他敢核对，口径能一次性固化成规则 |
| 项目作者 | 需要能反复跑评测、看 trace、做失败归因的工程环境 | 简历上那句带数字的话，只可能来自这个环境 |
| 技术面试官 | 只有 5-10 分钟，大概率没有 API key，可能在自己笔记本上离线跑 | 无 key 的 cassette 回放模式、一条命令启动、README 顶部 30 秒 GIF |

最后一类是真实且必须承认的约束型用户。很多设计决策（单容器、无 key 可跑、README 结构）是专门为他做的。

## 四、核心场景

### 场景 1：口径陷阱的自愈（招牌演示）

> 「2026 年上半年各商品分类的销售额排名」

模型第一次生成的 SQL 漏了订单状态过滤。口径规则 R1「金额类聚合必须约束 `orders.status`」通过 AST 谓词到达性检查拦下，把「缺失谓词：`orders.status='已完成'`」回喂模型；第二次通过，执行、出柱状图，结论明确写「已排除 1873 笔已取消和 2017 笔已退款订单」。

界面上两次尝试**并列保留**、可以左右对比 diff。一屏之内同时展示了规则引擎、对业务错误（而非语法错误）的自愈、以及可审计的执行过程。

### 场景 2：只偏 6.2% 的隐形错误被拦下

> 「毛利率最低的 5 个商品分类是哪些」

`products` 表有 `price` 和 `cost`，但 `order_items.unit_price` 是可能低于标准售价的促销成交价 —— 毛利必须用 `unit_price - cost`。规则 R2 在执行前命中并回喂修复。

这是「模型会写出语法完全正确但业务错误的 SQL」的典型题，也是最能说明「为什么口径要由代码强制」的一题。

### 场景 3：诚实拒答与澄清

> 「员工工资是多少」 / 「上个月复购率多少」

第一类：数据源里根本没有相关表。系统不编造、不返回空表、不崩溃，明确说明并列出可查询的 4 张表和 3 个示例问题。

第二类：口径本质歧义（复购率按自然月还是 90 天窗口）。系统给出两个澄清选项和各自的口径说明，用户点选后本次会话沿用该选择。

### 场景 4：撞上数据边界

> 「近 30 天华东地区的月度销售额趋势」

数据止于 2026-08-31，而系统当前日期是 2026-09-11。AS_OF_DATE 单一时钟取 `max(orders.created_at)`，把「近 30 天」确定性解析成 2026-08-02 至 2026-08-31 并**回显给用户**，而不是算出一段几乎没有数据的区间。

问月度趋势时，跨到 9 月的末点画成虚线并标注「本期数据不完整」，避免业务人员读成「业绩崩了」。

若查询返回 0 行，归因探针按启发式顺序逐层放宽过滤跑 `COUNT`，直接告诉用户是 `region='华东'` 这个条件把数据滤没了 —— 而不是让他对着空表猜工具是不是坏了。

### 场景 5：纠正回流与报表固化

模型写错了字段，用户在界面上直接改 SQL、点重跑、结果对了，一键「保存为纠正样本」（入库前先过安全检查和 EQP 预检，并要求用户确认结果正确）。这条纠正下次作为 few-shot 被**确定性地**检索出来注入。

同一次问答还能固化成命名报表，之后点一次直接出数 —— 走存下来的那条 SQL、不调模型、约 200ms 出图、零 token、同样输入永远同样输出。

这是把「一次性对话」变成「可复用资产」的关键，也是产品形态与 demo 的分界。

## 五、差异化能力

按重要性排序。每一条都注明了它最终能变成简历上的什么表述。

### 1. 口径规则引擎

8 条业务口径规则，以数据结构声明（规则 ID、严重级别 block/warn、触发条件、缺失谓词描述、中文修复建议）。用 `node-sql-parser` 解析模型生成的 SQL，在 WHERE / JOIN ON / 子查询 / CTE / HAVING 构成的作用域链上做**谓词到达性判定**，而不是字符串 contains。

- block 级违规 → 不执行，带着缺失的具体谓词回喂模型重生成
- warn 级违规 → 继续执行，但把答案降级为「未核验」并标注原因

每条规则强制配一个能真实触发它的用例和一个不该触发它的反例，在评测集上统计**误报率**，超过 5% 的规则降级或删除。

> **难点**：谓词到达性是真正的静态分析问题 —— 过滤条件可能出现在五种位置，可能被 `status <> '已取消' AND status <> '已退款'` 这种等价写法表达，还要处理别名解析和 CTE 作用域。更难的是假阳性成本极高：误判会把正确 SQL 打回、触发无谓重试，反而拉低准确率。

> **简历表述**：「把 8 条业务口径约束从提示词里挪进代码：用 SQL AST 的谓词到达性分析在执行前强制校验，违规时把缺失的具体谓词回喂模型重生成，实现了对业务错误（而非仅语法错误）的自愈。口径陷阱类题目准确率从 X% 提升到 Y%，规则误报率控制在 5% 以内。」

### 2. 三态输出与拒答校准

每个答案标注为「已核验 / 未核验 / 拒答」。触发降级或拒答的是**四类确定性条件**，不是模型的自我声明：

1. block 级口径规则在重试预算内未能修复
2. 结果形态可疑（空集 / 单个 NULL / 全零 / 行数正好等于 LIMIT 说明被静默截断 / 聚合建立在 0 行之上）
3. 问题涉及的实体在 schema 里不存在
4. 口径本质歧义

评测报告里**自信错答率**（系统声称已核验但结果错）、拒答率与准确率三个数并列上报，拒答率设硬上限 12%。

> **关键**：拒答必须校准，这是 precision/recall 权衡而不是一个开关。全拒答的系统自信错答率完美但毫无用处。所以评测集里必须同时有可答题和真不可答题（占比 ≥15%）。

> **简历表述**：「把「自信错答率」定义为一等评测指标并与准确率、拒答率三者并列上报：自信错答率从 X% 降到 Y%，代价是拒答率 Z%（硬上限 12%）。」

### 3. 确定性可复现的评测体系

30 题分层冻结评测集，题面**在写任何实现代码之前**定稿并 git 打 tag（commit 时间戳可查）。所有 LLM 请求按 `hash(模型 + 参数 + 规范化后的 messages)` 录制成 cassette，**一份基础设施三个用途**：

- CI 里 replay 跑全量当回归门禁（掉点或任何题回归，PR 直接 fail）
- 调优期十几轮重跑近乎免费
- 面试官无 key 时驱动完整产品演示

> **简历表述**：「建立了确定性可回归的 LLM 评测体系：30 题分层冻结集在实现之前定稿并打 tag，LLM 请求按哈希录制为 cassette，replay 模式下全量评测离线零成本运行并接入 CI 门禁。经 N 轮定向优化，总准确率从 X% 提升到 Y%。」

详见 [评测体系](06-evaluation.md)。

### 4. SQL 安全多层纵深

核心是**引擎级授权回调**：`node:sqlite` 的 `setAuthorizer` 在 SQLite 的 prepare 阶段拿到解析后的 `(action, 表, 列)` 三元组做白名单判定。因为拿到的是 SQLite 自己解析后的语义，注释拆词、大小写混写、全角字符、藏在 CTE 里的写操作**一概失效** —— 这是文本匹配永远做不到的。

> 绝大多数候选人的答案是「我做了关键字黑名单」。这个答案在面试官眼里等于没做。

详见 [安全设计](07-security.md)。

### 5. 手写 agent 主循环 + 可回放 trace

约 250 行、六步两工具，三处非标准设计：多维预算对象、基于 AST 规范化指纹的**环路检测**（防止模型在两个错误答案之间震荡）、失败六分类走六条不同的修复路径。

> 「重试 3 次」是每份教程都有的答案，面试官听腻了。真实故障是模型在两个都错的 SQL 之间来回抖动把配额烧光。

详见 [Agent 设计](05-agent-design.md)。

### 6. 面向非技术用户的可验证性

四件小东西：**口径回执卡片**（由 AST + 规则表机械生成、完全不经过模型，因而结构上不可能撒谎）、**AS_OF_DATE 单一时钟**、**不完整周期检测**、**空结果归因探针**。

> 给业务人员看 SQL 是给工程师看的安慰剂 —— 他们读不了。真正建立信任的是一张他们看得懂的中文回执。

## 六、能力清单

完整清单见 [需求与验收](01-requirements.md)。这里只列分级原则：

- **P0（必做，26 项）** —— 没有它项目就不成立。含主链路、安全四层、agent 循环、口径引擎、评测体系、部署。
- **P1（应做，8 项）** —— 有它才叫产品。含空结果归因、不完整周期、纠正回流、报表固化、CI 门禁。

## 七、明确不做

这份清单和能力清单同等重要 —— 敢写下「不做」本身就是取舍。完整清单（36 条）见 [需求与验收](01-requirements.md#明确不做)，这里列最关键的几条和理由：

| 不做什么 | 为什么 |
|---|---|
| 完整语义层（QueryPlan IR + SQL 编译器 + join 路径求解器） | 通往 Cube.js 克隆。4 张表的 join 路径写死是十几行代码，通用求解器是几周且面试零加分。用 8 条口径规则拿走它 80% 的叙事 |
| 迁移到 PostgreSQL | 已实测 `node:sqlite` 的 `setAuthorizer` 可用，比「只读角色 + SET TRANSACTION READ ONLY」更硬核也更便宜。换 PG 是为一个已有更好答案的问题付账 |
| 向量检索做 few-shot 召回 | 理由不是「4 张表用不上」，而是**向量召回引入不确定性，同一道评测题两次跑出不同上下文，准确率变化再也无法归因** —— 它会摧毁花两周建起来的评测体系 |
| 多数据源 / 用户填 DSN | 工作量以周计，而面试官根本无法验证（他不会把自己的库连上来）。只保留一个 Connector 接口接缝 |
| 自由多轮追问 / 指代消解 | 它把评测从无状态变成有状态，直接摧毁项目里最值钱的资产。替代方案是「以此问题为基础继续问」按钮，三行代码拿 80% 体验 |
| 任何 agent 框架（LangChain / LangGraph） | 一行 import 换掉整个项目的核心价值 |
| 多 agent 编排 / planner + critic | 只是把不确定性叠加，简历上写「多智能体协作」在筛简历时反而引起警惕 |
| 治理层（认证绿标、审核队列、RBAC、审计导出） | 两周工作量，演示时只有几秒钟镜头，面试零加分 |

## 八、这个项目凭什么不是 demo

一个 demo 和一个产品的区别不在功能多少，在于**能不能回答「你怎么知道它是对的」**。

- demo 的演示脚本是一条 happy path；GateSQL 的招牌演示是**它拦下了一个错误答案**
- demo 说「准确率还不错」；GateSQL 给出分层准确率、自信错答率、拒答率三个数，以及每一轮优化的 before/after
- demo 的安全是关键字黑名单；GateSQL 的安全是引擎级授权回调 + 30 条攻击语料测试，每一层都能说出「它防住了哪一层防不住的东西」
- demo 跑完就没了；GateSQL 每次运行落结构化 trace，失败不是消失而是变成优化依据
- demo 需要你配好环境才能看；GateSQL 不配任何 API key 也能 `docker compose up` 走完整个流程
